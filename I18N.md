# Built-in i18n

Import `TranslationManager` from `@azure-net/kit/i18n` and pass the instance to
`createApp` through `useTranslations`. No external translation package is required.

## Define translations

```ts
// src/core/translations/index.ts
import { TranslationManager } from '@azure-net/kit/i18n';

export const translations = new TranslationManager({
	messages: {
		en: () => import('./locales/en.js').then((module) => module.default),
		ru: () => import('./locales/ru.js').then((module) => module.default)
	},
	initLang: 'en',
	initLangFromAcceptLanguage: true,
	cookieName: 'language'
});

export const { t } = translations;
```

Construction and destructuring `t` are safe at module scope: neither resolves
server context. The class delegates lazily to RegisterProvider. Each server
request owns its locale, dictionaries, pending loads and reactive state. The
browser has one provider instance per manager.

Call `t` and read manager getters only within an active server request or in the
browser. Do not call the instance as a factory. `createTranslations` remains
available for compatibility; prefer `new TranslationManager(...)` for new code.

## Register with createApp

```ts
// src/program.ts
import { createApp } from '@azure-net/kit';
import { translations } from './core/translations/index.js';

export const { register } = createApp((app) => app.useTranslations(translations));
```

Keep the app's plugin/lifecycle wiring enabled. Call `register()` in the root
layout before rendering consumers:

```svelte
<script lang="ts">
	import { register } from '../program.js';
	import type { Snippet } from 'svelte';

	register();
	const { children }: { children: Snippet } = $props();
</script>

{@render children()}
```

`useTranslations` owns the translation lifecycle. Do not add manual preload,
client initialization or state synchronization calls to application hooks.

1. On the server, the app preloads the selected dictionary before rendering.
   Selection uses a supported cookie first, then `Accept-Language` when enabled
   (including quality ordering and regional fallback), then `initLang`.
2. The app transforms the HTML opening tag to set `lang` and
   `data-azure-net-locale`. It also replaces an optional `%lang%` placeholder.
3. In the browser, `clientInit` runs before hydration and before boot. It reads
   the HTML locale marker and awaits that locale's dictionary import before
   invoking the app's `useClientInit` callback. Do not postpone this loading to
   `useClient` or depend on boot state being available during `clientInit`.
4. During root-layout registration, boot synchronizes the locale snapshot before
   the app's `useBoot` callback and reuses the already-loaded dictionary. Repeated
   synchronization does not overwrite subsequent client locale changes.

Only locale metadata is transferred in i18n boot state:

```ts
{
	currLocale: 'en',
	i18n: { default: { locale: 'en' } }
}
```

Dictionaries are **not serialized into HTML or boot state**. The server loads its
dictionary for SSR; the browser imports its dictionary separately before
hydration. Rendered HTML naturally contains translated text, not a dictionary
payload. These state fields are typed by the kit; no custom declaration is needed.
The optional `prefix` changes the snapshot key from `default`.

With SSR disabled there is no server marker. Client initialization selects a
supported cookie, then browser language preferences when enabled, then `initLang`.
It still awaits dictionary loading before the first render through the app's
client-init lifecycle. Failed initialization can be retried.

## Components

```svelte
<script lang="ts">
	import { translations, t } from './core/translations/index.js';
	const { switchLocale } = translations;
</script>

<h1>{t('login.title')}</h1>
<p>{translations.locale}</p>
<button onclick={() => switchLocale('ru')}>RU</button>
```

Adjust the import path for the component's location. The exported `t` remains
reactive because every call reads the active provider's rune state. No `$t` or
`$locale` store syntax is needed. Do not destructure `locale` if it must remain
reactive; read `translations.locale` in markup or a `$derived` expression.

`switchLocale` is client-only. It reuses loaded dictionaries, deduplicates pending
imports, and applies only the latest requested switch. It updates the configured
cookie and document language. `subscribeLocaleChangeEvent(listener)` returns an
unsubscribe function. `translations.locales` exposes the available locale names.

The package demo retains the export name `TranslationManager` for its instance
and exports `t` alongside it. Its components import that instance directly rather
than calling `TranslationManager()`.

## Message syntax

- Variables: `Hello {{name}}`, rendered with `t('greeting', { name: 'Sam' })`.
- Plurals: `{{count | plural:item,items,items}}`, following TextUtil conventions.
- Object arguments: `t({ key: 'greeting', vars: { name: 'Sam' } })`.
- Missing keys return the key; inherited object properties are not translations.

Dictionaries use `$state.raw`, not deep proxies; treat them as immutable. Render
translated strings as text, not with `{@html}`. Browser-importable dictionaries
are public assets: never include secrets or private user data. Personalized HTML
must not be shared through a public response cache.
