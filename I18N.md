# Built-in i18n

Import from `@azure-net/kit/i18n`. Neither edges nor edges-translations is used.

```ts
import { createTranslations } from '@azure-net/kit/i18n';
export const TranslationManager = createTranslations({
	messages: {
		en: () => import('./Locales/En').then((m) => m.default),
		ru: () => import('./Locales/Ru').then((m) => m.default)
	},
	initLang: 'en',
	initLangFromAcceptLanguage: true,
	cookieName: 'language'
});
```

Declaration at module scope is safe. Call the returned accessor only inside an
active server request or in the browser. RegisterProvider gives each request its
own manager, dictionaries, in-flight requests and rune state. In the browser it
returns one instance per factory. No process-wide user locale exists.

## program.ts

```ts
export const { register } = createApp((app) =>
	app
		.useServer(async ({ event, resolve }) => {
			const manager = TranslationManager();
			await manager.preloadTranslation();
			return resolve(event, {
				transformPageChunk: ({ html }) => manager.applyHtmlLocaleAttr(html)
			});
		})
		.useBoot(({ state }) => {
			TranslationManager().syncFromState(state);
		})
		.useClient(() => TranslationManager().initializeClient())
);
```

Call register() in the root layout before resolving consumers. In app.html,
use `<html lang="%lang%">` if using applyHtmlLocaleAttr.

preloadTranslation() detects cookie first, then Accept-Language (quality and
regional fallback), then initLang. An optional asynchronous resolver overrides
detection. It automatically writes RequestContext.current().state.currLocale and
state.i18n snapshots containing the selected dictionaries. Those fields are typed
by the kit; no custom declaration is required.

syncFromState(state) is synchronous and uses only its argument, never server
context in the browser. It restores both locale and dictionary, so the first
client render matches SSR without a second fetch. Subsequent calls on the same
instance do nothing, preserving client edits. A prefix option isolates snapshots
for separate managers (use distinct prefixes); each snapshot carries its own
locale. currLocale reflects the most recently preloaded manager.

When SSR is disabled, state can be empty. initializeClient() loads initLang (or
the locale supplied by state), updates document language and can retry after a
failed import. Put it in useClient, not useClientInit or layout load: those run
before useBoot. Pure CSR can briefly render translation keys while loading.

## Components

```svelte
<script lang="ts">
	import { TranslationManager } from '#platform/Bootstrap/Localization';
	const manager = TranslationManager();
	const { t, switchLocale } = manager;
</script>

<h1>{t('login.title')}</h1>
<p>{manager.locale}</p>
<button onclick={() => switchLocale('ru')}>RU</button>
```

No $t or $locale store syntax. t is safe to destructure: it reads active rune
state on each call. Do not destructure locale if it must remain reactive.
Dictionaries use $state.raw, not deep proxies. Treat translation objects as
immutable and render translated strings normally, not with {@html}.

switchLocale() is client-only, reuses loaded dictionaries, deduplicates concurrent
imports and applies only the latest requested switch. It updates the configured
cookie and document language. subscribeLocaleChangeEvent(listener) returns an
unsubscribe function. Server preload and client switching are deliberately separate.

Variables: `Hello {{name}}`. Plurals retain the existing TextUtil convention:
`{{count | plural:item,items,items}}`. t also accepts `{ key, vars }`. Missing keys
return the key; inherited object properties are never resolved as translations.

Only public dictionaries should enter request state: hydratable exposes them to
the client. Do not place tokens, services or private data in translation payloads.
Personalized HTML must not be shared in a public response cache.
